Configuration parameters

Reference of config.toml for traffic (the traffic commands; Python package trafico), the simulation of vehicle flow on a road segment with a traffic light. Every parameter of a run is read from this file. The train simulation (rail) is documented separately, in rail.html.

Usage and general rules

uv run traffic                              # root config.toml → results/<ID>_run/
uv run traffic hora_pico                    # root config.toml → results/<ID>_hora_pico/
uv run traffic results/<ID>_hora_pico    # config.toml of that folder (replica of the run)
uv run traffic-view                          # movement of the latest run (see [animation])
uv run traffic-view results/<ID>_hora_pico --start 300 --duration 60
uv run traffic-variants --lengths 50 150 300 --lights 40/20 30/30 20/40 --lanes 1 2 --without bike bus
uv run traffic-emissions --bumps none 100 --light no --length 200 --lanes 1 2 --without bike motorbike carga
  • The file is always called config.toml. The command's only argument is optional: if it is an existing folder, its config.toml is read; otherwise it is the name of the run and the config.toml at the project root is used. Text containing / that does not exist as a folder is an error, not a name.
  • Missing keys take the default value given in the tables.
  • An unknown key (for example, a typo), a wrong type or an out-of-range value stops the run with a message that names the key.
  • Each run creates results/<YYYYMMDD-HHMMSS>_<name>/ with the plot, the summary, the series and a copy of the configuration used. That copy records the seed and the name, so it is enough to replicate the run with identical results.
  • The plot has six rows of panels: two per vehicle type (cumulative passengers and passenger flow; passengers per metre of occupied lane are no longer plotted, but remain in series.csv as pax_per_m) and four per lane: saturation over time, the vehicles crossing the light against the capacity of their exit queue (see [exit]), the entry queue to the segment next to the exit queue (two panels side by side, each with its own scale) and the mean speed as a violin. Each violin shows the distribution of the lane's mean speed (distance over time of its vehicles, including stopped ones) across all samples of all replicas in which the lane had vehicles. Inside it carries the interquartile range (bar) and the median (dot), and the lane label gives the median, the interquartile range and the fraction of time with vehicles. That way a lane with few vehicles, like the bus lane, does not oscillate: it only counts when someone is there. The time series, smoothed over 10 s, remains in series.csv. Pax·km/h are no longer plotted, but remain in series.csv.
  • summary.txt includes the row «Mean speed (km/h)» for each type: the distance travelled inside the segment divided by the time its vehicles spent in it during the whole run, counting the time stopped (light, stop, bottleneck, exit queue) and not counting the wait in the entry queue. It includes those carrying goods. Compare it with the type's maximum speed to see how much the segment slows it down.
  • [vehicles.<key>] speed_kmh is now a dictionary {min, max, mean, std}, like length: each vehicle draws its maximum speed. With variable speed, the run header shows the line «Variable maximum speed» and the violin reference lines give the mean and the range (e.g. «auto 75 (60–90)»). With std = 0 the results are the same as with a plain number.
  • Bikes can overtake within their lane: with [vehicles.bike] pass_in_lane = true (requires abreast ≥ 2) and variable speeds, the faster one passes the slower one on one side. Without pass_in_lane, or with all at the same speed, the results do not change.
  • [vehicles.<key>] accel and decel (m/s²): gradual acceleration and braking with anticipation. Without them, speed changes are still instantaneous and the results do not change. With them the queue starts more slowly (in the six-car test, ~1.7 s between cars instead of 1.5 s, and the first one loses ~1.5 s more) and the run header says so.
  • New section [exit]: exit queue per lane after the light, with a capacity (veh/min) and a length (storage, in m); if the next vehicle does not fit, it closes the line of that lane and saturates it. By default capacity = 0 (no exit queue, same results). The plot adds a panel per lane with the vehicles crossing the line against the capacity of their exit queue, and another row with the entry queue to the segment next to the exit queue. The video shows, to the right of each lane with an exit queue, the metres occupied against its length.
  • [output] csv is now called series_csv, and the new emisiones_csv decides whether emissions_by_position.csv is written (before, always). Older copies with csv still work: its value is used, with a warning.
  • [output] show was removed (it opened the matplotlib window in addition to saving the plot). Older copies have it: it is ignored with a warning. Instead, mobility_plot, passengers_plot and emissions_plot decide which plots are drawn.
  • [behavior] congestion_factor was removed. It slowed down moving vehicles in proportion to the queue of stopped vehicles in the whole lane, even those ahead of it, and depended on length. In practice it barely changed the results (in the Insurgentes configuration, 661 cars with the factor against 661 without it; the queue discharge, identical), and what it meant to represent is already covered by the gradual dynamics (accel/decel), the chain reaction and queue_reaction. Older copies have it: it is ignored with a warning, and if it is a list it still counts for the number of lanes. The saturation panel no longer shows the factor, and overtaking compares only real speeds.
  • New key [traffic_light] free_lanes: lanes without a light (e.g. a continuous turn). It only applies to the types with an exclusive lane in them: they keep going on red and do not slow down on yellow. The run header lists those types. traffic-variants --lanes also keeps the exit queue and the light-free lanes of the chosen lanes.
  • New key [traffic_light] enabled: with false the street has no traffic light, the same as with red, green and yellow at 0.
  • New command traffic-emissions: compares the emissions of a street without a speed bump, with bumps at different positions and with or without a traffic light, with the same seed.
  • Several traffic lights: a street can have more than one ([[traffic_light]], one section per light), each with its position, its red, green and yellow phases, its start_phase and its free_lanes. The one without position is the one at the end of the segment, where flows and queues are measured.
  • New option pedestrian in [speed_bump] and in each [[traffic_light]]. With it a speed bump is also a pedestrian crossing (vehicles stop completely while someone is crossing) and a light is a pedestrian light (green for vehicles except when pedestrians are waiting, and only when the previous light is red). The arrival of pedestrians is the random variable pedestrian_crossing (pedestrians/min). Without pedestrian the results do not change.
  • New named coefficient sets, chosen with [vehicles.<key>.emissions] source: int_panis_2006 (the original ones) and sedema_cdmx_2018 (recalibrated with Mexico City's vehicle inspection program: car, taxi, pickup and LPG minibus). config.toml now uses the SEDEMA ones for the car and includes the types taxi, carga_ligera and colectivo with no demand.
  • New fuel consumption and cost: [vehicles.<key>] fuel and mass_kg, section [fuel] with the price per litre. The summary gives L/100 km, mL and cost per trip, the extra spent compared with free flow, the run total and the efficiency at constant speed; series.csv, the L/min per type.
  • New emissions (model by Int Panis et al., 2006): CO2, NOx, VOC and PM per type, in summary.txt (per km, per trip, excess compared with free flow and a table accelerating from 0 to 80 km/h), in the plot and in emissions_by_position.png/.csv. They require accel and decel.
  • New option traffic-emissions --light-spacing: the sweep of the spacing between two fixed-cycle lights (the second one red when the platoon from the first arrives), with the footprint on both sides of the light (queue and acceleration), the delay and the warning of a queue reaching the entry. New key [[traffic_light]] offset (offset in s) to coordinate lights. Offsets red, green (green wave) and same (same phase), one per segment, and mixed chains with --fixed-spacings.
  • New key [vehicles.<key>] time_headway (s): following headway while moving; behind a moving leader the vehicle keeps gap_stop + time_headway · v (like IDM's s0 + v·T) instead of a fixed gap_run, which with gradual dynamics gave about 0.9 s between cars at 50 km/h and a capacity twice the real one. Without it, everything stays the same. See calibration.
  • New command traffic-calibrate: measures a vehicle type (the car by default) in standard situations (discharge of a queue on green, continuous flow, stopped queue) and compares it with reference values (saturation flow, start-up lost time, capacity, jam density).
  • Faster: traffic-emissions (also with --spacing) spreads the replicas of all scenarios over a single process pool and honours [execution] workers = 0 (as many as CPUs; before it ran in a single process), and each engine step is ~20 % faster with gradual acceleration and braking. The results are identical to the previous ones with the same seed.
  • Compiled engine: the simulation step (src/trafico/kernel.py) is compiled with numba and runs ~40 times faster (one replica of 9,000 simulated s with two lanes, a pedestrian light and two speed bumps: from 24 s to 0.6 s; 4 replicas in parallel: from 49 s to 1.8 s). The results are bit-for-bit identical to the previous ones with the same seed. The first run after installing or after changing kernel.py compiles the engine (~1 min) and saves it in src/trafico/__pycache__; later runs load it in under 1 s. See [execution].
  • New Python API (trafico.api) and results.json: each run writes a JSON summary with a stable format and the commands accept --json (prints that JSON to stdout); the API runs the same as the commands with named arguments and returns the result already parsed.
  • New option traffic-emissions --spacing: sweep of the distance between two speed bumps that computes the additivity of their emissions, the mean over the segment, the excess between them, the gradient along the segment, the cost of each added bump, the footprint of a bump and the minimum spacing to dilute it, with a figure and tables.
  • Several independent speed bumps: a street can have more than one ([[speed_bump]], one section per bump), each with its position (now a number, not a list), its lanes and its pedestrians. Older copies with position = [35, 70] still load: each position is a bump with the other keys of the section, with a warning. In traffic-emissions, --bumps 35,70 is a scenario with two bumps.
  • New section [speed_bump] (bump at position m, in the lanes lanes) and key [vehicles.<key>] speed_bump_kmh: the maximum speed at which each type goes over the bump. traffic-variants --lanes keeps the bump in the chosen lanes.
  • [behavior] queue_reaction = true: the stopped entry queue starts with a reaction time, like the rest of the queue, instead of entering already moving. It corrects the excess flow on segments shorter than the queue. Default false (previous results do not change); the run header says when it is active.
  • passenger_distribution.png shows, for each participating type, the percentage of vehicles with each number of passengers: all those that arrived during the simulation, adding up the replicas, with their observed mean. A step line marks the expected distribution according to the configured pax (the rounded normal truncated to the range used by the draw), to tell the noise of a small sample from a real problem. If the range has more than 30 values, the bars are grouped in bins (of 5 passengers for a range from 1 to 120).

Comparing variants: traffic-variants

Runs the same configuration with each combination of segment length and light split, and plots, for each length, the mean speed of each lane (bars per split) and the vehicles in the entry queue over time (one line per split). All scenarios use the same seeds, so the differences come from the variant and not from chance.

Comparing emissions: traffic-emissions

Runs the same street without a speed bump and with bumps at the requested positions (and, optionally, with and without a traffic light) and compares the emissions. All scenarios use the same seed: the same vehicles arrive, with the same passengers and speeds, so the differences come from the bump or the light. It plots the flow leaving the segment over time, the vehicles per minute of each type, the emissions per km of each type and pollutant (with the change compared with the first scenario) and the emissions along the street.

uv run traffic-emissions [name | folder] [options]
uv run traffic-emissions calle200 --bumps none 100 --light no --length 200 --lanes 1 2 --without bike motorbike carga
uv run traffic-emissions --bumps none 50 100 150            # where the bump is best placed
uv run traffic-emissions --bumps none 100 50,100 25,50,75  # one, two or three bumps on the same street
uv run traffic-emissions --light both                   # each bump with and without a light
uv run traffic-emissions --spacing                      # how far apart must two bumps be to dilute the footprint?
uv run traffic-emissions --spacing 30 50 70 --first-bump 35
uv run traffic-emissions --spacing 10 20 30 40 --chain 4   # chain of 4 bumps: cost of each added bump
uv run traffic-emissions --light-spacing                # how far apart must two lights be?
uv run traffic-emissions --light-spacing 50 100 200 --cycle 40/20/3 --first-light 120
uv run traffic-emissions --light-spacing 25 50 75 --offset green   # green wave
uv run traffic-emissions --light-spacing 25 50 75 --chain 3 --fixed-spacings 150 --offset green,red

Spacing between speed bumps: --spacing

A speed bump leaves a footprint on the emission profile: just before it, emissions drop (the car brakes and emits less than when cruising), just after it they spike (it accelerates) and the wake decays until the vehicle recovers its speed. If the second bump falls inside that wake, the footprints overlap. --spacing looks for the smallest distance that keeps them apart. It runs, with the same seed, the street without a bump, with one bump at --first-bump (P1) and with two bumps at P1 and P1 + d for each d (with --chain N, with N bumps at P1, P1 + d, …). Each bump is the [[speed_bump]] at that position or, if there is none, a copy of the first one (lanes and pedestrians). A d that does not fit in the segment (the last bump must be 5 m or more from the end) is skipped with a warning.

With the emission profile of each scenario (g/(m·h), all lanes), E, and that of the street without a bump, base, for each pollutant:

  • Additivity R(d) = N(d) / (n·N1), with n the bumps in the chain (2 by default), N the net excess ∫ (E − base) dx of the chain and N1 that of a single bump. 1 = the chain emits like n isolated bumps; less than 1, the wakes overlap (the car does not manage to recover its speed).
  • Cost of each added bump (N − N1) / ((n − 1)·N1), in isolated bumps, and per metre of spacing (100 · cost / d, in % of an isolated bump). It is the extra emitted by a bump right next to the previous ones: 1 = as much as a single one. For the pair it equals 2R − 1. It grows with d and reaches 1 where the chain is additive; the cost per metre measures the penalty of the slow zone that each spacing adds.
  • Footprint: distance, after a single bump, until its excess falls below the threshold (10 % by default) of its peak. It is of the order of the distance over which the vehicle accelerates from the bump speed to cruising speed.
  • Mean over the segment: the mean of E over [P1, Pn + footprint] (Pn, the last bump) divided by that of the street without a bump over the same segment.
  • Excess between bumps: the mean of E − base between the first and the second bump (leaving out 5 m next to each one) as % of the peak of a single bump.
  • Gradient: the mean of |dE/dx| (5 m intervals) over the whole segment [P1, Pn + footprint], the same as the mean. It does not use inner windows, so it does not jump when the edge of a window falls on the braking ramp or the wake of a bump; it is also defined when the bumps are right next to each other. It is the mean variation of the profile: rises and falls count the same, and it decreases with the spacing because the same peaks are spread over a longer segment. That is why it has no minimum of its own and does not enter the minimum spacing. In the figure it is shown as % of the maximum slope of a single bump.

The minimum spacing is the smallest one in the list where the pair is additive (|R − 1| ≤ tolerance) and the second bump is outside the footprint of the first one (d ≥ footprint); the largest across pollutants is taken. Additivity demands somewhat more than the footprint (in the example, 60 against 48 m) because the second bump starts slowing the car down some 15–20 m before reaching it. There is no interpolation: if none in the list qualifies, it says so and you should widen --spacing. Smaller spacings usually emit less in total (the car accelerates only once) but leave a high plateau with no recovery between the bumps.

The folder contains bump_spacing.png (additivity, mean over the segment, excess between bumps, gradient over the segment and cost of each added bump, total and per metre, against the spacing, one line per pollutant, and the CO₂ profile of some spacings), summary.txt, bump_spacing.csv (metrics per spacing and pollutant), spacing_profiles.csv, data.npz, scenarios.json (with "modo": "separacion") and base_config.toml. There are 2 + (number of spacings) scenarios times the replicas: --replicas and --run make it shorter. The values hold for the cruising speed, accel and speed_bump_kmh of the configuration.

Spacing between traffic lights: --light-spacing

The same for traffic lights: at what distance can a second red light be placed without changing the footprint of the first? It runs, with the same seed, the street without a light, with one at --first-light (P1) and with two at P1 and P1 + d (or N with --chain). Only the lights of the sweep are present, all fixed-cycle with the phases of --cycle: the light at the end of the segment, the intermediate ones and the bumps of the configuration are removed (with --bumps 35,100 fixed bumps are kept in all scenarios). With the red offset, the i-th light gets offset = i · (red + τ(d)) (modulo the cycle), with τ(d) the time the head of the platoon takes to cover d from a standstill: it accelerates with its accel up to its free-flow speed and keeps that speed. That way it turns red just as the platoon that left the previous light on green arrives, at any spacing: the worst case. With green the delay is just τ(d): it turns green just as the platoon arrives (green wave). The head is the type with the highest rate (tipo_peloton and viaje_s in scenarios.json). A fixed offset of red does not work: the platoon takes longer to arrive the farther away the second light is, and with a large d it already finds it green (a green wave). Without --length, the segment is extended if needed to P1 + (N − 1)·dmax + 150 m.

The same metrics as with the bumps are computed, with these differences:

  • Two-sided footprint: before the light, the queue and the braking (L_antes, up to the farthest point before P1 where the excess of a single light exceeds the threshold of the peak); after it, the acceleration (L_después). The second light is outside the footprint of the first if d ≥ L_antes + L_después, and the mean and the gradient are computed over [P1 − L_antes, Pn + L_después].
  • Stable, not additive: at an isolated light only those arriving on red stop; with the red offset the whole platoon stops at the second one. That is why the pair does not tend to two isolated lights (R stays above 1 even far apart) but to the distant pair. The minimum spacing is the smallest from which the pair's emission stays within ±tolerance of that of the most separated pair in the list (÷ lejana in the summary), at that d and all larger ones, and also d ≥ L_antes + L_después. The most separated pair alone does not count as a plateau: if only it qualifies, you are asked to widen the list. R of the most separated pair is the cost of the red coordination compared with isolated lights.
  • Queue up to the entry: with a short d the queue of the second light reaches the first one and that of both can reach the entry of the segment. Then arrivals are cut off and fewer vehicles get through: those spacings are marked with * in the summary and with a hollow dot in the figure, and they do not count for the minimum spacing.
  • ≡ isolated (n · R): the extra emission of the chain counted in single lights. In a perfect green wave the pair is ≈ 1 (the second light stops nobody); with the mixed chain green,red it is compared with the red pair spaced the same as the first and last lights.
  • Delay: the travel time added by the chain ÷ (n × that of a single light), with the mean weighted by the crossing vehicles. Out: the vehicles leaving the segment ÷ those of the street without a light.

The folder (light_spacing by default) contains light_spacing.png, light_spacing.csv, spacing_profiles.csv, summary.txt, data.npz, scenarios.json (with "elemento": "semaforo", the cycle and the offset), base_config.toml and results.json. The footprint of the single light is shaded in the CO₂ profile of the figure.

Python API and results.json

To use the simulator from a program (a script, a notebook, an agent) without parsing text or opening CSV files, there are two things that do not change between versions as long as their number does not go up: the results.json file in each results folder and the trafico.api module.

results.json and --json

Each command (traffic, traffic-variants, traffic-emissions, with or without --spacing) writes results.json when it finishes. With --json, the command prints that same JSON to stdout and sends everything else (summary, progress, warnings) to stderr:

uv run traffic-emissions --spacing 20 40 60 --chain 3 --json 2>/dev/null | python -c "import json,sys; print(json.load(sys.stdin)['metricas']['recomendada_m'])"
uv run traffic-emissions --redraw results/<ID>_bump_emissions --json    # also with comparisons already run

The header is the same in every mode:

  • emisiones: escenarios, each with nombre, topes_m, semaforo and, per type, veh_min, tiempo_recorrido_s, velocidad_media_kmh and per pollutant por_km, cambio_pct (compared with the referencia scenario) and exceso_flujo_libre_pct; parametros is the scenarios.json.
  • separacion: distancias_m, recomendada_m, huella_m, topes_por_cadena and, per pollutant, one value per spacing of aditividad, media_tramo, exceso_entre, gradiente_tramo, costo_tope and costo_por_m (see spacing between bumps), plus d_aditiva, d_huella and d_minima.
  • variantes: escenarios per segment and light, with velocidad_kmh_por_carril, cola_final, cola_maxima and cruzan.

Format rules: keys are lowercase ASCII with the unit at the end (_s, _m, _kmh, _pct); NaN and infinities are written as null (strict JSON); a key never changes its meaning or unit, and new keys can be added without changing schema. Folders of comparisons and sweeps made before this version do not have it: the API rebuilds it from their raw data without writing anything; old traffic runs have to be run again. Folders written before the output files were renamed to English keep their Spanish names (resultados.json, escenarios.json, variantes.json, datos.npz, resumen.txt, calibracion.csv): they are still read, listed and redrawn.

Calibration: traffic-calibrate

Measures how a vehicle type of the configuration behaves in three standard traffic engineering situations and compares it with reference values. Each measurement uses a one-lane segment with only that type (no bumps, stops, bottlenecks or pedestrians), with its speed, length, gaps, accel, decel and the behaviour of [behavior], and the limit of its lane.

uv run traffic-calibrate                     # the car with config.toml
uv run traffic-calibrate --vehicle motorbike --queues 50
uv run traffic-calibrate results/<ID>_run --json
  • Discharge of a queue on green: after a 120 s red, the headway between line crossings (vehicle front) of the first 15 in the queue is measured, over --queues queues with different seeds. The saturation headway is the mean from the 5th position on; the saturation flow, 3600 divided by that headway; the start-up lost time (HCM), the sum of the extra time taken by the first 4 positions.
  • Continuous flow without a light, 600 m, with demands from 10 to 120 veh/min for 900 s (the first quarter does not count): flow at the exit and density in the middle third. The capacity is the highest flow and the headway at capacity, 3600 divided by it.
  • Jam density: 1000 / (length + gap_stop) vehicles per lane-km in a stopped queue.

[initial] Initial condition

By default the segment starts empty and fills up with the demand. With occupancy the lanes already have vehicles at t = 0, so the behaviour with a loaded road can be observed from the start, without waiting for it to fill.

KeyTypeDefaultDescriptionConstraint
occupancynumber or list0.0 Fraction of each lane occupied at the start: the sum of length + gap_stop of its vehicles divided by [road] length. With 1, the lane is a compact queue, with each vehicle at its gap_stop from the one ahead (the model's minimum distance); with 0, empty. A number applies to all lanes; a list gives one value per lane, starting from the right one, and its length must match the other per-lane lists (see [road]). Each value in [0, 1].

How each lane is filled:

  • Vehicles are placed until the occupancy is reached. If one does not fit, another one is drawn (e.g. a shorter one), so the lane is as full as requested.
  • The free space is first shared so that each vehicle has its gap_run and starts moving; what is left is shared at random. If it is not enough (high occupancy), all are compressed equally and start stopped, like a traffic jam: they start with their reaction time when room opens up ahead, and the queue stretches out. As a reference, a lane of cars (4.5 m, gap_stop 1, gap_run 4) starts moving up to an occupancy of ~0.65.
  • If the light starts on red, the first ones form the queue at the stop line.
  • The type of each vehicle is drawn in proportion to its rate in [demand], among the types that can use that lane. Exclusive and fixed lanes are respected, so an exclusive bus lane fills up only with buses. It is best to give it a low occupancy with a list, e.g. [0.2, 0.6, 0.6, 0.05].
  • Passengers, goods (cargo_prob) and length are drawn as for arrivals. Buses that start past their stop do not stop there.
  • They use their own random generator: the demand arrivals are the same with or without an initial condition, and with 0 the run is identical to that of an empty segment.

Initial vehicles count in the traffic, in the crossings and in the crossing passengers, but not as demand arrivals («Arrivals (veh/min)»). They do not count in the mean travel time either, because they did not travel the whole segment. summary.txt shows them in the row «On the segment at the start», and the header gives the occupancy of each lane.

[exit] Exit queue

After the light each lane flows into an exit queue (the street ahead) that accepts a limited number of vehicles per minute and is storage m long. If more cross the line than it accepts, the queue fills up, the line of that lane closes even on green and the lane saturates: the queue of stopped vehicles grows backwards and fewer vehicles cross.

KeyTypeDefaultDescriptionConstraint
capacitynumber or list0 Vehicles per minute accepted by the exit queue of each lane; 0 = no exit queue (crossing the line is enough, as before). A number applies to all lanes; a list gives one value per lane, starting from the right one, and its length must match the other per-lane lists (see [road]), e.g. [0, 12, 15, 0]. Each value ≥ 0.
storagenumber or list60 Length in metres of the exit queue of each lane. Each vehicle takes up its length plus its gap_stop in it (a 4.5 m car, 5.5 m; a 1.8 m bike, 2.3 m), so 60 m are ~11 cars. Whoever crosses the line enters it and leaves at a rate of capacity, in order of arrival. If the next vehicle does not fit in the free metres, the line of that lane closes for it as on red; a bike may fit where a car no longer does. An empty queue accepts anyone, even if it is shorter than the vehicle. Each value > 0 m.

How it works:

  • What counts is the lane in which the vehicle crosses the line (the origin lane, if it is changing lanes). A vehicle changing towards a lane whose exit queue has no room for it cannot cross either.
  • Those waiting at the closed line stop at it and, when there is room for them, start with their reaction time, as when the light turns green. With decel, the closed line is respected in advance just like red.
  • The exit queue empties continuously: at 12 veh/min one vehicle leaves every 5 s. With no vehicles waiting it does not store up departures for later.
  • The plot has the panel «Vehicles crossing the traffic light per lane (one-cycle window, …) against the capacity of their exit queue»: the demand at the line of each lane and its exit capacity as a dotted line. If the demand touches the capacity, the exit is the limiting factor.
  • Below, the row «Entry queue to the segment per lane» | «Exit queue after the traffic light per lane» compares what is waiting to enter the segment (in vehicles) with what has already crossed and is waiting to leave (in occupied m); the exit length is a dotted line. They are two panels with their own scale because the entry queue can grow without limit and the exit queue cannot exceed storage. With the exit saturated, the exit queue stays stuck at its limit and the entry queue grows: saturation propagates backwards to the entry of the segment. Without an exit queue, the right panel says so.
  • summary.txt shows the line «Crossing the traffic light per lane (veh/min)» and, with an exit queue, «Line closed by the exit queue (% of the time, …)»: the fraction of time in which the next vehicle of the lane did not fit. series.csv adds the columns crossing_veh_min_lane<N>, entry_queue_veh_lane<N> and, with an exit queue, exit_queue_m_lane<N> (occupied m).
  • In the video, the «exit» column to the right of the light shows the exit queue of each lane that has one as «occupied m/length» (e.g. 33/55 m), in red when the next vehicle does not fit and the line of that lane is closed even though the light is green.

Example (with the Insurgentes configuration on a 100 m segment): with capacity = [0, 6, 8, 0] and storage = 55 (10 cars) lanes 1 and 2 let through 6.1 and 8.1 veh/min, stuck at their capacity, their line is closed by the exit queue 23 % and 16 % of the time, and the crossing cars drop from 667 to 496. With [0, 12, 15, 0] the exit never fills up: only 8.3 and 10.6 veh/min go through those lanes, so the light is still the limiting factor.

How it works:

  • Without decel, the vehicle drops at once to the bump speed in the step in which it would reach it and returns to its speed as soon as it has fully passed it, like the other instantaneous changes of the model.
  • With decel it brakes earlier, without exceeding decel, to reach the bump at its speed, and then accelerates at most at accel. Whoever comes behind treats it like any slower leader.
  • A vehicle changing lanes respects the bump if it is in its origin or destination lane. Whoever is behind one braking for the bump can move to a lane without a bump if it pays off.
  • With several bumps, each one is handled separately: the vehicle brakes before each, recovers speed between them (if the distance allows; with very close bumps it barely accelerates) and goes over each at most at its speed_bump_kmh.   • The run header gives the positions, the lanes and the speed of each type; in the video each bump is a striped band and in the space-time diagram, a «bump» line on its lanes.

Pedestrians: pedestrian

A speed bump ([[speed_bump]]) or a traffic light ([[traffic_light]]) with pedestrian = true lets pedestrians cross. Pedestrians appear at random and do not depend on the vehicles: pedestrian_crossing is their random variable, in pedestrians per minute, with the same format as the rates of [demand] (normal(mean, std) truncated to [min, max], drawn again every rate_interval; within the interval arrivals are Poisson). The whole schedule of a replica is computed when it is created, with its own generators: enabling pedestrians does not change the vehicle arrivals or their draws, so the comparison with the same seed still holds.

Pedestrian crossing at a speed bump

  • Each pedestrian waits 3 s at the kerb (yellow phase: vehicles see them) and crosses in pedestrian_time s (red phase). The crossing is closed while someone is crossing: whoever arrives during the crossing extends it, so several pedestrians in a row keep it closed for longer.
  • On yellow, whoever can still brake at their decel stops with the front at the bump; whoever can no longer do so goes through (the same rule as a light's yellow). Types without decel stop dead.
  • On red all types with their front before the bump stop, even those without speed_bump_kmh, and only in the bump's lanes. When the crossing ends they start with their usual reaction time ([behavior] reaction).
  • With several bumps, each one ([[speed_bump]]) has its own configuration and its own pedestrians.

Pedestrian light

  • It is green for vehicles while nobody is waiting. Arriving pedestrians queue; with someone in the queue the light turns yellow (yellow), then red (red: the time it takes everyone waiting at the start of the red to cross) and back to green. Those arriving during the red wait for the next crossing.
  • It does not trigger immediately. Before turning yellow, the minimum green green must have passed since the previous crossing (with green = 0, none), and, if there is another fixed-cycle light before it (towards the entry of the segment), that one must be red. Without a previous light it only waits for the yellow. Other pedestrian lights do not count as previous, because they have no cycle.
  • It can be intermediate or the one at the end of the segment. It has no start_phase (it always starts green) and it is not the reference light of the plots: it defines neither the flow window nor the phase shading, which follow the last fixed-cycle light.
  • free_lanes works the same as on a normal light.

What the run shows

  • The header describes the pedestrian crossing or the pedestrian light and which light it coordinates with. summary.txt has a «Pedestrians» block per point: how many crossed, how many closures, the mean wait, and the seconds and percentage of time it was red for vehicles (mean across replicas).
  • The space-time diagram marks the yellow and red of each pedestrian crossing and light on its line, with the phases of the recorded replica (they change with the pedestrians of each replica). The video paints the crossing in the colour of its phase.
  • Crossings add stops and starts, so they raise the travel time, the emissions and the fuel. traffic-emissions keeps the bump's pedestrians in every scenario with a bump and has none in the «no bump» scenario. traffic-variants replaces the light at the end of the segment with a fixed-cycle one, even if it is a pedestrian light.

Limitations. The pedestrian is exogenous: they cross even if a vehicle is already on the crossing (the model does not make them wait), and whoever goes through during the yellow does not see them. All pedestrians take the same time to cross. There is no lane or sidewalk: only the time the crossing is closed.

[bottleneck] Bottlenecks

Situations that reduce the capacity of the road. The first option is halts: some vehicles stop for a while in their lane (a breakdown, someone getting on or off, a delivery). Those coming behind treat them like any stopped vehicle: they compress behind it or, if the lane next to it allows, change lanes to overtake it (see leader_slowdown in [behavior]). Nothing else needs to be configured for that effect.

This section defines where the halts happen. Who stops, with what probability and for how long is defined in each vehicle type, with bottleneck_prob, bottleneck_time_mean and bottleneck_time_std in [vehicles.<key>]. A type without bottleneck_prob does not stop. With no type with a probability > 0 there are no halts and the run is identical to one without this section.

Emissions

Estimate of CO2, NOx, VOC (volatile organic compounds) and PM (particulate matter) with the instantaneous emission model of Int Panis, Broekx and Liu (2006), Modelling instantaneous traffic emission and the influence of traffic speed limits, Sci. Total Environ. 371:270–285, the same one used by Aimsun. At each step, each vehicle emits E = max(0, f1 + f2·v + f3·v² + f4·a + f5·a² + f6·v·a) g/s, with its speed v (m/s) and its acceleration a (m/s²). It is meant to compare scenarios (with and without a bump, with and without a light, more or less demand): the model was fitted with a European fleet from the early 2000s, it does not include CO or cold starts, and its absolute values are an approximation.

Each type carries its coefficients in [vehicles.<key>.emissions], one list [f1, f2, f3, f4, f5, f6] per pollutant (co2, nox, voc, pm). <pollutant>_decel gives those for a < −0.5 m/s² (by default, the same ones). A type without the section, or without accel and decel, does not emit: without gradual dynamics acceleration is instantaneous (from 0 to 50 km/h in one step) and the model does not apply. So that an emergency stop does not blow up the a² term, the acceleration that enters the model is capped to [−decel, accel].

  • summary.txt, «Efficiency at constant speed»: L/100 km, km/L and cost per km at 20, 40, 60 and 80 km/h (up to the type's maximum speed), with the model and with a physical reference curve.
  • series.csv: columns fuel_l_min_<type> (litres per minute).
  • The run header: the fuel and price of each type, and those that have fuel but no CO2 (the bus and goods vehicles, which only have PM or nothing).

The two efficiency curves. The model's is Int Panis CO2 at zero acceleration: it was fitted with real urban driving (small accelerations, a fleet from twenty years ago), and per km it always falls as speed rises; above ≈ 70–80 km/h it is below what overcoming air resistance demands. The physical one (Willans line) is the model's idle plus the wheel power needed to overcome rolling and air resistance, VSP = 0.132·v + 0.000302·v³ kW/t times the mass (mass_kg), divided by a marginal engine efficiency of 24.6 % and the heating value of the fuel; that efficiency makes the 1250 kg car at 77.7 km/h do 18.6 km/L, the highway median of the 4-cylinder, 1.4–2.0 L petrol cars in the CONUEE 2026 catalogue. About sample

sample only decides how often the plot and CSV series are recorded. It does not change the simulation: with the same seed exactly the same vehicles drive and the summary comes out the same with any value.

ValueAdvantageCost
Small (0.1–0.5 s)More detail: each start after the green, the stretching of the queue, each crossing. CSV and series memory 2 to 10 times larger; somewhat slower.
1 s (default)Good balance for light phases of tens of seconds.—
Large (5–10 s)Small CSV and little memory in runs of many hours. Less detail and risk of aliasing.

Aliasing with the traffic light. Passengers per metre of lane and the saturation of each lane are instantaneous snapshots at each sample. If sample gets close to the cycle length, the snapshots always fall in the same phase and the curve is misleading. It should not exceed ~1/10 of the shortest phase (≤ 3 s with 30 s phases).

Cumulative passengers, the flow in pax/min, pax·km/h and the mean speed of each lane lose no information: they are accumulated at each 0.1 s step and sampling only groups them.

  • The smoothing windows (one cycle for the flow, 10 s for pax·km/h and the speed per lane) are measured in samples and rounded if sample does not divide those durations. If sample exceeds 10 s, the moving average stops smoothing.
  • If the simulated duration is not a multiple of sample, the last stretch does not enter the series; the summary does include it.

About replicas

A replica is a complete, independent run, with the same configuration but another sequence of random numbers: arrivals, passengers per vehicle, reaction times, duration of lane changes and tie-breaks when choosing a lane. Repeating it N times (Monte Carlo) estimates the typical behaviour and how much it varies. The plot shows the mean ± 1σ across replicas.

  • Seeds: they are derived from the base seed, one per replica. The result does not depend on workers, and going from 8 to 16 replicas the first 8 remain the same.
  • More replicas, a more precise mean: the error of the mean is σ/√N; with 4 times more replicas it is halved.
  • The shaded band does not get narrower: ±1σ measures how much one run varies from another, and that variation belongs to the system. More replicas only estimate it better.
  • Infrequent types need more replicas. With 16 replicas, cars (268 ± 11 passengers) are within ±2 % at 95 %, and buses (277 ± 132) within ±24 %. For ±10 % on buses about 85 replicas would be needed; a longer run also helps.
  • Cost: time grows linearly with N and is divided among the processes; memory hardly grows, because aggregation is done online. N should be a multiple of workers.
  • Few replicas: with 1 there is no σ (band of width 0) and with 2–3 σ is unreliable.

Recommendation: 8–16 replicas to explore; 30 or more to report. To choose N with data, use the «± σ across replicas» of the summary: N ≈ (1.96 · σ / desired margin)².
